Cab booking — storage changes & test checklist
What the cab schema consolidation changed, and how to verify the new columns are actually
being written.

Audience: tester. Everything below is "do this action, then look at this table column and
expect this value."

Finding a booking's rows (no SQL needed — use your DB browser's filter box):

booking → filter booking_reference = the reference the API returned. Note its id.
booking_item → filter booking_id = that id, service_type = cabs. Note its id.
booking_item_cab → filter booking_item_id = that id. This is the main row. Note its id.
booking_item_cab_location, booking_item_cab_assignment, booking_item_cab_trip → filter booking_item_cab_id = the id from step 3.
booking_item_status_history → filter booking_item_id = the id from step 2.
Tables went from 6 to 4: booking_item_cab_vehicle and booking_item_cab_operator no
longer exist (their data is now inside booking_item_cab).

PART A — Test checklist
A1. Create a cab booking
Action: complete a booking through finalize-booking, or through create-booking +
payment. Do it for an AIRPORT / DEPARTURE journey.

A1.3 booking_item_cab.extra_km_rate — the important one
The provider sends a text label; we now store a whole number in paise (rupees × 100).

/fare sends extraKmFareLabel	extra_km_rate must be
INR 24/Km	2400
INR 19/Km	1900
INR 18.5/Km	1850
INR 23/Km	2300
INR 32/Km	3200
Fail if: the value is 24 (not multiplied), 1849 (wrong rounding on the decimal case),
or 0. Empty is acceptable only when the provider sent no label at all.

A1.4 booking_item_cab_location — new address and airport_code
There are two rows, location_type = PICKUP and DROP.

Column	Expect
address	the full address, on both rows, when the request carried one
airport_code	filled on exactly one row — see the table below
Which row carries airport_code:

journey_type	travel_type	Meaning	Row with the code
AIRPORT	DEPARTURE	going to the airport	DROP
AIRPORT	ARRIVAL	coming from the airport	PICKUP
RENTAL or OUTSTATION	anything	no airport involved	neither — both empty
Fail if: the code is on both rows, on the wrong row, or on neither for an AIRPORT
journey. Please test both DEPARTURE and ARRIVAL — they use opposite rows and a swap is
the most likely bug here.

A1.5 booking_item_cab — old columns must now stay empty
These columns still exist (they are removed in a later migration) but nothing should write
them any more. On a newly created booking they must be empty / zero:

Column	Expect on a new booking
airport_code	empty (it moved to the location row)
extra_km_fare_label	empty (replaced by extra_km_rate)
price_reference	empty
payment_redirect_url	empty
activated_at	empty
cab_assigned	0
cab_left_for_pickup	0
cab_reached_source	0
cab_trip_started	0
cab_trip_end	0
Fail if any of these is populated on a booking created after the release — it means old
code is still running or a write path was missed.

A1.6 booking_item_cab.search_id
Must be filled for every new booking (a long uuid|hash string). It is allowed to be empty
only on bookings made before this release.

A2. Provider sends /update-booking
Action: trigger the provider update callback (or have the provider send it).

Table.column	Expect
booking_item_cab.provider_booking_id	the provider's booking id from the payload
booking_item_cab.update_booking_response	the whole raw payload as text
booking_item_cab_assignment	a row exists when the payload carried an assignment block
…_assignment.driver_name, driver_mobile, vehicle_registration_no, tracking_url, assigned_at	values from the payload
This is a fix — please test it specifically. The same callback can arrive on two
endpoints, and one of them used to ignore the assignment block entirely:

v1/airportServices/cabs/update-booking — always worked
api/airportServices/updateAirportServiceBooking — used to drop the driver details
Send the callback with an assignment block to both endpoints and confirm the
booking_item_cab_assignment row appears either way.

Also new on the second endpoint: if the payload's bookingId does not match the
provider_booking_id already stored for that booking, the API now answers 400
"bookingId does not match the provider booking id for this booking" and writes nothing.
That is correct behaviour, not a bug. It applies to cab bookings only — other services are
unaffected.

A3. Partner webhooks — the trip lifecycle
The five progress flags are gone. Each event now writes a row in
booking_item_status_history instead.

Action: send each partner webhook event in order.

Event sent	New row in booking_item_status_history linked to a booking_status_mapping with status_code	Replaces the old flag
DRIVER_CAB_DETAILS	310	cab_assigned
TRIP_LOCATION, event contains left	320	cab_left_for_pickup
TRIP_LOCATION, event = arrived	330	cab_reached_source
TRIP_DETAILS, tripEvent = start	340	cab_trip_started
TRIP_DETAILS, tripEvent = stop	350	cab_trip_end
For each row also check:

Column	Expect
provider_timestamp	the timeStamp from the webhook, unchanged — a 13-digit number like 1750935000000
occurred_at	when we processed it (may differ from provider_timestamp — that is fine)
status_mapping_id	points at the cabs row for that status code
Also check booking_item.current_status_mapping_id advances to the newest status.

Additional checks:

DRIVER_CAB_DETAILS also creates/updates a booking_item_cab_assignment row (driver name, mobile, vehicle name/colour/registration, partner, synced_at). Re-sending the same event must not duplicate the row; a reassignment (different sync_datetime) must add a new row and keep the old one.
BOOKING_CONFIRMED must fill booking_item_cab.otp.
TRIP_DETAILS must also fill booking_item_cab_trip (started_at, ended_at, distance and fare fields) — unchanged from before.
Re-sending the same event must not create a second identical status row.
After a cancellation: if a TRIP_LOCATION webhook arrives after the booking is cancelled, a history row is still recorded but booking_item.current_status_mapping_id must stay on cancelled — it must not go back to "driver arrived".
A3.1 The OTP now has one home
Column	Expect
booking_item_cab.otp	the trip OTP, from the BOOKING_CONFIRMED webhook
booking_item_cab_assignment.trip_otp	stays empty — no longer written
Fail if: a booking reaches "driver assigned" with an empty otp — that means the
BOOKING_CONFIRMED webhook never arrived, which is now the only source.

A5. Other services must be unaffected
The status-history table and the generic update endpoint are shared. Please smoke-test one
booking of each type end to end and confirm nothing changed:

eSIM · Lounge · Fast Track · Attractions · Flight · Hotel
For those, booking_item_status_history.provider_timestamp will simply be empty — that
is correct, only cab partner webhooks carry a provider timestamp.

B6. Progress flags → status history
Was, in booking_item_cab	Now, a row in booking_item_status_history with status_code
cab_assigned = 1	310 — driver assigned
cab_left_for_pickup = 1	320 — driver on the way
cab_reached_source = 1	330 — driver arrived
cab_trip_started = 1	340 — trip in progress
cab_trip_end = 1	350 — trip completed
"Flag was 1" now means "a row with that status code exists for the booking item". The
advantage: each row also records when it happened.

Old bookings were not converted. A booking completed before this release has no
310-350 rows, so its trip timeline shows as empty. That is expected, not a bug.

B7. booking_item_status_history.provider_timestamp — new column
Holds	the time the provider says the event happened
Format	epoch milliseconds, 13 digits, e.g. 1750935000000
Comes from	the partner webhook's timeStamp field, stored exactly as sent
Empty when	the status change came from us, not a provider — so it is empty for every non-cab service
occurred_at still means "when we recorded it". The two can differ by minutes if a webhook
was retried — that is normal.

booking_item_cab_assignment.trip_otp	duplicated booking_item_cab.otp
the five progress flags	replaced by status history, B6
