What changed, in one paragraph
A fareType=CORPORATE,NORMAL search used to ask Riya for everything, filter out fares matching a corporate label list, and call whatever remained "normal" — a guess that nothing verified. Each fare type is now a lane with its own cache entry and category, and a fare's category comes from Riya's own per-fare tag rather than from pattern-matching its label. A fare that nothing positively identifies is dropped and alerted rather than shown under a category nobody checked.

Normal, corporate and SME all arrive from a single vendor call, so a plain normal search leaves corporate and SME already cached. That matters against Riya's 250:1 look-to-book budget far more than it matters for speed.

Before you start
Provider metadata that must be set
On provider riya-flights-prod-api. Classification depends on these — wrong values produce plausible-looking but wrong categories, which is exactly the failure mode to watch for.

Key	Value	Note
RiyaFareClassificationMode	indicator	Default. whitelist is the fallback only.
RiyaCorporateAirlines	SG,QP,IX	Vendor-confirmed
RiyaSmeAirlines	6E,AI	Vendor-confirmed
RiyaFareIndicatorMap	{"I":"CORPORATE"}	Temporary — recovers IX corporate. Removed once Riya emits C.
RiyaIgnoredFareIndicators	B,S	Products we do not sell; dropped silently
RiyaCorporateFareType	corporate labels	Renamed from RiyaFareType, which stays for V1
RiyaSmeFareType	SME labels	6E's SME label is literally "Corporate"
A metadata change takes up to 10 minutes, or a restart
Three caches sit between the database and the classifier, and the policy service keeps its own 10-minute copy downstream of the metadata cache. Clearing the metadata cache alone is not enough. If a config change appears not to have taken effect, this is usually why — wait ten minutes or restart, rather than concluding the value is wrong.

Known and expected
A lone corporate or SME search now makes two vendor calls, not one. Deliberate — the narrowed call proved unreliable. The second call fills all three categories, so the next search on that route is free.
Riya's response size varies between identical calls. Two calls seconds apart returned 568 and 722 items. Results cache until end of day, so a route can legitimately show fewer options than a repeat search would. Not a bug in this branch, but it will look like flakiness — please note the route and time rather than filing it as a lane defect.
Riya is changing the SME fare type (their message of 2 Sep, API and frontend). If SME behaviour looks wrong, check whether their change has landed before raising it.
Six pre-existing unit-test failures are unrelated to this branch and were deliberately left alone.
./mvnw test-compile is currently broken by an unrelated cab change (#1428) — does not affect the running application.
Reporting a defect
Please include:

The full request body, and pid / tierId / subscriptionId
X-Correlation-ID if you set one — it makes the server log searchable
Route, date and the time of the search, since results cache until midnight
Whether the response was COMPLETE or still INPROGRESS
Any v2.corpFare lines from logs/server.log around that time
For anything about a missing or miscategorised fare, the v2.corpFare lines are usually the whole answer — they name the vendor tag and the labels for each dropped or disputed fare.
